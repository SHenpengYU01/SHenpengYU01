    ROB+Tomasulo

    1. 公式速记

    • Amdahl：\(\mathrm{Speedup} = 1 / (1-f+f/N)\)
    • Roofline：\(AI = \mathrm{Flops}/\mathrm{Bytes}\)
    • Little's Law：并发度 = 延迟 × 吞吐

    2. 三类 Hazards

    类型 原因 处理
    结构性 资源冲突 加资源/分离资源
    数据性 指令间依赖 转发、停顿、ROB
    控制性 分支方向未定 预测、冲刷

    3. 数据依赖

    类型 例子 是否真相关 结论
    RAW I1写，I2读 是 只能转发/停顿
    WAR I1读，I2写 否 需重命名
    WAW I1写，I2写 否 需重命名
    • WAR和WAW因寄存器数量有限导致,重命名可解决

    4. RAW 的典型处理

    • Forwarding / Bypass：把 EX/MEM/WB 的结果直接送回 EX 输入。
    • 优先级：MEM > WB。
    • 经典例子：lw -> add。lw 结果在 MEM 末才可用，不能直接转发到下一条 EX，需插入 1 个 bubble。
    • Stall：StallF=1, StallD=1，FlushE=1。

    5. Precise Exceptions

    • 异常时：前面的指令必须全部 commit，后面的指令都不能 commit。
    • 目的：保持冯·诺依曼顺序语义、便于恢复和调试。
    • ROB 是实现精确异常的核心。

    6. ROB 工作流程

    1. in-order Decode：按序分配 ROB entry。
    2. OoO Execute：乱序执行，结果先写 ROB。
    3. in-order Commit：按序写回寄存器/内存。

    7. ROB 关键字段

    • V：结果是否 ready
    • DestRegID：目标寄存器
    • DestRegVal：结果值
    • StoreAddr/Data：存储信息
    • PC / Exception?

    8. ROB 的作用与代价

    • 优点：支持精确异常、消除 WAR/WAW、适合多周期执行单元。
    • 缺点：硬件复杂，读结果要间接查 ROB，功耗和面积更大。

    9. 考点速记

    • 多周期指令（如 DIV）难点：后续指令可能先完成 → 用 ROB 保证顺序提交。
    • lw -> and：常考，需 1-cycle stall + forward。
    • 异常处理顺序：冻结/冲刷 → 保证精确状态 → 保存 PC/寄存器 → 跳转 handler。
    • ROB 大小：参考 Little's Law，窗口越大越好，但硬件代价也越大。

    1. Why OoO？

    • In-order 里，一条长延迟指令会把后面的独立指令也挡住。
    • OoO 让“数据已就绪”的指令先执行，提升吞吐。

    2. 组件

    • RS 缓冲已译码但未执行的指令，等操作数就绪后发给 FU
    • RAT(Alising Table) 记录寄存器当前对应的 RS Tag，做重命名
    • CDB 广播 {Tag, Value}，唤醒等待的 RS

    3. Tomasulo 算法四阶段

    (1) Issue（译码/分配）—— In-order

    • 检查 RS 是否有空闲条目；若无 → Stall。
    • 分配 RS 条目（分配 Tag = 条目 ID）。
    • 源操作数：
    • 查 RAT：若该寄存器 Valid=1 → 直接取值填入 RS（.v=1）。
    • 若 Valid=0 → 取 RAT 中的 Tag 填入 RS（.v=0），等待 CDB 广播该 Tag。
    • 目的寄存器：将 RAT 中该寄存器项改为 当前 RS 条目 Tag，并置 Valid=0（表示值尚未产生）。

    (2) RS（等待/唤醒）—— Out-of-order

    • 监听 CDB，若广播 Tag 匹配某个源操作数的 Tag → 将值写入该源，置 .v=1。
    • 当 所有源操作数 .v=1 → 指令“唤醒 (Wakeup)”。

    (3) Execute（执行）

    • 从唤醒的指令中选择 (Select) 一个派发到对应 FU（仲裁）。
    • FU 执行，产生结果（可能多周期）。

    (4) Writeback (WB) —— 广播到 CDB

    • 仲裁获得 CDB 使用权。
    • 广播 {Tag, Value}。
    • 更新 RAT：若 RAT 中某寄存器 Tag 匹配广播 Tag → 写入 Value，置 Valid=1。
    • 更新 RS：所有 RS 条目中源 Tag 匹配 → 写入 Value，置 .v=1。

    4. 寄存器重命名如何消除假依赖（WAR / WAW）

    • 示例：ADD R5 ← R3, R4 和 MUL R5 ← R6, R7（WAW）。
    • 在 Issue 阶段，两条指令的目的寄存器 R5 被重命名为不同的 RS Tag（如 a 和 b）。
    • 后续读 R5 的指令通过 RAT 指向最新的 Tag，因此 WAW/WAR 自然消失
    • 本质：RS 条目充当了无限数量的“物理寄存器”。

    5. Tomasulo vs. 记分板

    • Scoreboard：遇到 WAR/WAW 会停顿。
    • Tomasulo：重命名后不必停顿，结构更复杂。

    6. ROB-precise exception

    • 两阶段流水线（“双驼峰”）：
    • 前段（RS）：乱序派发/执行（容忍延迟）。
    • 后段（ROB）：乱序完成，顺序提交 (In-order Commit)。
    • RAT 双份：
    • Frontend RAT (Future Map)：指令执行完成后立即更新（投机状态）。
    • Architectural RAT：仅在 ROB 提交（Commit）时更新（精确状态）。
    • 异常处理：冲刷投机指令，将 Architectural RAT 复制回 Frontend RAT → 恢复精确状态。

    7. 关键性能限制

    • 指令窗口 (Instruction Window) = RS 中未发射 + ROB 中未提交的指令总数。
    • 窗口越大，可发现的并行性越高，但硬件（CAM、仲裁）开销剧增。
    • 延迟容忍度：由窗口大小决定；若一条长延迟指令，需巨大窗口才能继续填充独立指令。
