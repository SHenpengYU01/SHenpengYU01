    7.8

    • 目标：从整体上明确问题定义，以及研究方向：

    理解师兄的说明

    说明原文如下：

    首先可以了解Anthropic的Skill、结构，调用的原理，progressive disclosure。
不过，科研中的skill，虽然借鉴了Anthropic的skill，通常简化很多，比如往往是单个文件，也没有progressive disclosure机制。更像是把一段guideline插入提示词context中。另外，业界skill常常是human-crafted（比如CC库里面的那些），而科研时，很多方法的skill，是LLM自己自动生成。

skill的研究大概聚焦于这几个方面：

- skill的自动生成、迭代（refine）。如果单个task有多个skill，还会涉及到检索。生成往往基于对正确、错误trajectory的提炼。
- skill+self-evolution等机制，比如不训练policy，只迭代skill。
- skill+训练的方法，比如训练policy model更好地使用skill。也有训练skill generator的。

聚焦的任务，以agent的居多，但总体比较广泛。

和skill方法比较相似的，是experience-based method (Expel)、procedural memory这些早期工作。区别可能在于skill对raw trajectory的加工更多，另一方面就是踩了Anthropic skill的热点

一些代表性论文——

方法类：
- skillRL，Trace2Skill（skill merge的机制），SkillX（skill的level划分），CoEvoSkills（结合self-evolution）、Ctx2Skill（和你的工作比较像）、SkillOS（训练skill generator，我觉得意义有限）
另外我觉得还不错的：MemSkill（memory任务，和SkillRL像）、SkillRouter（讨论skill的retrieval）、XSkill（比较normal，多模态）、D2Skill。
eval类：
- skillsbench：基于海量的skill做评测。和科研自己构造的那种skill差别较大。你的工作应该用不到

    个人理解：

    • 上述主要说明了Skill的研究方向和已有的相关工作
    • 做的是Agent Skill相关内容，本质是提示词工程的演进：Agent = LLM + Harness，Skill是一种Harness。我们的目标是提升Agent解决各种问题（编码、问答、数学等不同领域）的能力，LLM改变不了，只能改变Harness。Harness最初只是简答的提示词，后来演进为结构性的框架，不过本质还是LLM的输入，改变的是输入内容的管理方式（Prompt为手动管理，而harness框架可以通过约束让LLM自己管理上下文）。

    Skill基础概念

    《Equipping agents for the real world with Agent Skills》 - 链接：https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills - 说明：Anthropic发布Agent Skills的官方工程博客，是理解Skill概念的第一手材料。详细介绍了Skill的目录结构、SKILL.md格式、YAML frontmatter以及Progressive Disclosure的三层设计。

    《Building Agents with Skills: Equipping Agents for Specialized Work》 - 链接：https://claude.com/blog/building-agents-with-skills-equipping-agents-for-specialized-work - 说明：后续博文，解释了为什么从“构建专用Agent”转向“构建Skill”这一范式转变，以及Skill如何把通用Agent变成领域专家。

    Agent Skills开放标准官网 - 链接：https://agentskills.io/ - 说明：Anthropic于2025年12月将Agent Skills发布为开放标准。

    anthropics/skills - 链接：https://github.com/anthropics/skills - 说明：Anthropic官方Skill示例库，包含PDF处理等真实Skill案例。可以直观理解Skill的文件结构和写法。

    Progressive Disclosure

    渐进式披露 是其核心设计理念，采用三层架构：

    层级 内容 加载时机
    第一层 元数据（技能名称、简短描述） 智能体启动时预加载到系统提示
    第二层 SKILL.md完整内容 模型判断技能相关时加载
    第三层 附加文件（脚本、参考资料等） 按需加载或执行

    这种设计让技能库可以包含海量信息却不怕超出上下文窗口限制。科研场景中的skill通常简化很多——往往是单个文件、没有progressive disclosure机制，本质上就是把一段guideline插入prompt context中。

    Ctx2Skill

    Ctx2Skill 通过对抗性自我对弈（挑战者与推理者各带 Proposer/Generator 协同进化）与动态选择机制（跨时间重放，乘积式解决率 + 拉普拉斯平滑），巧妙绕过"无反馈"与"高成本"两大障碍。实验设计全面：宏观有跨模型/跨类别的解决率，微观有五维度技能质量评估与详尽消融/变体分析，并验证了技能的可迁移性与可解释性。整体证明：在不更新参数、不依赖外部信号的前提下，仅凭上下文本身即可自主演化出有效、可复用、可解释的自然语言技能。

    个人理解：

    • Ctx2Skill 设计了一个多LM循环对抗的Skill生成框架，并且通过self-replay机制动态地选择历史skill中，那些能平衡解决最容易与最难问题的最优skill，这有效增强了该系统的鲁棒性。
    • 我学习到的核心思想：对抗式生成，注意解决对抗式生成中生成越来越极端偏置的问题，找到生成的平衡点

    Cultural-MT

    CULTURE-MT 的核心贡献在于把"翻译好不好"从字面正确性推进到"文化有效性"——译文是否让目标语读者正确理解原意并产生相当的情感共鸣。论文构建了首个面向社媒 UGC 翻译的多领域、多形态基准（1,002 条 × 14 领域 × 4 类型），并显式区分"文化负载符号"与"UGC 特定语言风格"两个被既有工作混淆的维度。配套训练的 JUDGER（微调 Qwen3-32B，准确率 86.03%、κ=0.72）使大规模自动评测成为可能。实验用 15 个模型证明：传统 BLEU/ChrF/COMET 对文化差异几乎失明，而文化有效性呈现清晰 scaling 趋势；基于 Qwen3-8B 的文化有效性自我精炼训练将 3 分样本从 4.09% 提升至 28.24%，且在多基准上 Ineff. 最低，仅以边际通用性能代价换取显著 UGC 增益。整体证明：面向文化感知 UGC 生成，必须超越字面正确性、走向文化有效翻译。

    7.14

    • 找主题相关的工作：多智能体（社媒）翻译，整理入 multi-agent-translation-survey.md

    检索方法

    • 用 firecrawl research 语义检索（多角度提问：多智能体协作翻译 / translator+evaluator 协同进化 / 自奖励翻译 / 社媒文化翻译 / 评估器漂移与 reward hacking）。
    • 关键论文全文深读验证：RIVAL（arXiv:2506.05070）、SCORE（arXiv:2606.04507）。

    核心结论

    Q1：translator + evaluator 协同进化有人做过吗？-- 做过，但不在我的交叉点上。

    • 翻译域已有 RIVAL：RM 与 LLM 交替更新、对抗 min-max、做字幕翻译，但仍受 reward hacking 困扰。这是最大撞车风险。
    • 通用域：Mutual-Taught、Cooper、Self-Rewarding LM、Meta-Rewarding。
    • 其他任务：SCORE（深度研究，直接点出"静态评估器无法随求解器进化"的痛点）、JarvisEvo（图像编辑）、TriPlay-RL（安全）。
    • 真实空白：在社媒 UGC + 文化有效性翻译上，用 NL 结构化评估器（非标量 RM）与翻译器协同进化，以 Ctx2Skill 式 cross-time replay 抗漂移（非对抗、非在线重训 RM）--无人做过。

    Q2：多智能体翻译四类范式：角色分工（TransAgents/TACTIC/MAATS）、评估侧多智能体（M-MAD）、对抗博弈（RIVAL/Dual Learning）、自精炼自奖励（SSR-Zero/TEaR）。

    对创新点定位的约束

    • 不能宣称"首创 translator+evaluator 协同进化"--RIVAL 已做。
    • 三差异化：① NL 文化有效性评估器 vs 标量 RM；② 社媒 UGC + 情感共鸣 vs 字幕；③ cross-time replay 抗漂移 vs 对抗 min-max / 在线重训 RM。
    • 动机有 precedents：SCORE 提出"静态评估器无法随求解器进化"，Spontaneous Reward Hacking 实证自评 reward hacking。
    • 附带发现可补 benchmark.md 的基准：CSM-MTBench（中文社媒，直接对照）、Xiaohongshu MT in the Wild（同平台用户侧）等 8 个。

    7.27

    梳理trace2skill论文：

    Trace2Skill 将大量 agent 执行轨迹（成功+失败）并行分析、提出轨迹级 skill patch， 再通过层次化合并（many-to-one consolidation）压缩为一个静态可移植技能目录。 支持 deepening（从人工技能出发补全）和 creation（从弱 LLM 草稿创建）两种模式。 实验覆盖 spreadsheet、数学、DocVQA、PDF/PPTX/DOCX，演化后技能可跨模型规模、 跨模型家族、跨分布（OOD）迁移。

    个人理解：

    • 核心 idea 是把 agent 踩过的坑和走通的流程归纳为可复用 SOP： 轨迹经验 > 参数生成技能 > 无技能；静态合并技能 > 检索式 memory > 顺序编辑。
    • 三个关键设计决策值得记住：
    • 并行 many-to-one consolidation vs 顺序编辑：解耦 trace 分析顺序依赖， 高频模式自动提升为 SOP，低频细节路由到 references，效率高很多。
    • 静态技能目录 vs 测试时检索 memory：把证据归纳为全局规则而非 isolated memory 条目，避免检索质量波动，也无需测试时检索开销。
    • Agentic error analyst vs 单次 LLM 错误分析：能检查 artifact、对比 ground truth、验证 fix，避免把日志表象当成根因——这对文件/工具型 agent 任务尤其重要。
    • 与 Ctx2Skill 的对比：Ctx2Skill 是对抗生成 + 动态选择（无轨迹，仅靠上下文 自我对弈），Trace2Skill 是轨迹归纳 + 静态合并（有轨迹，用执行信号驱动）。 两者都产出可迁移的自然语言技能，但信号来源不同——前者靠模型自己出题自己评， 后者靠真实执行结果的成败反馈。
    • 对我工作的启示：如果社媒翻译 agent 能收集到执行轨迹（成功/失败翻译案例）， 可以用 Trace2Skill 的思路把常见翻译陷阱和工作流归纳为技能；层次化合并机制 也可以用来合并多个语言对/领域下的 patch。

    7.28

    梳理skillrl论文：

    • SkillRL 的核心 idea 是：不要把 agent 的历史经验当成 raw memory 反复检索， 而是先把成功/失败轨迹蒸馏成更紧凑的 skill，再把这些 skill 放进 RL 训练循环里， 让 技能库与策略共同演化。
    • 这篇工作最重要的三点设计：
    • experience-based distillation：成功轨迹提炼“该怎么做”， 失败轨迹提炼“哪里会错、为什么错、下次如何避免”， 让 failure 也成为高价值训练信号。
    • hierarchical SkillBank：把技能分成 general skills 和 task-specific skills，前者提供跨任务策略原则， 后者补充环境/任务专属套路。
    • recursive skill evolution：当验证集暴露新 failure mode 时， 不只是继续调 policy，还会补写/改写技能库，形成 “policy 变强 → 暴露新问题 → skill 补全 → policy 再提升”的闭环。
    • 和普通 memory 方法相比，SkillRL 真正强调的是 abstraction 优于记忆本身：raw trajectory 虽然信息全， 但噪声大、token 重、难迁移；skill 是压缩过的可执行经验。
    • 对我工作的启发：如果希望 agent 真正持续进化， 不能只做轨迹存档或 episodic retrieval，而要把经验整理成结构化技能， 并让这些技能参与后续训练/推理过程。

    7.29

    梳理skillx论文：

    • SkillX 的核心 idea 是：用强 agent 的执行经验，自动构建一个 可检索、可迁移、可插拔的分层 SkillKB，再把它注入给较弱的 base agents， 让弱模型直接站在强模型积累的经验上工作。
    • 它和 SkillRL 很像，都是把经验从 raw memory 提升成 skill；但 SkillX 更强调 技能知识库本身的结构设计与迁移使用，而不是 skill 与 RL policy 的联合优化。
    • SkillX 最值得记住的三点设计：
    • Multi-Level Skills Design：把技能拆成 planning / functional / atomic 三层， 分别对应高层规划、中层功能套路和底层 API/工具细节。
    • Iterative Skills Refinement：SkillKB 不是一次性提炼完就结束， 而是根据新轨迹持续做合并、过滤、改写，逐步压缩冗余、提升表达质量。
    • Exploratory Skills Expansion：不仅被动总结已有数据，还会主动探索 低覆盖区域和高失败模式，补出训练数据里原本没有显式出现的新技能。
    • 这篇工作的关键判断是：可迁移经验不能只是“保留经历”，而要整理成 分层、条目化、轻量检索 的 skill 结构；这样才能既压缩上下文，又提升跨模型迁移性。
    • 对我工作的启发：如果后续要做 agent skill system，重点不只是“存什么经验”， 更是“按什么抽象层级组织经验、如何持续 refinement、以及如何把 skill 以低成本注入推理过程”。

    7.30

    梳理coevoskills论文：

    • CoEvoSkills 的核心 idea 是：复杂 agent skill 不能只靠一次性写出来， 而要让 skill generator 和 surrogate verifier 一起协同进化—— 一边反复修 skill，一边反复补测试，逐步逼近隐藏 oracle 的真实要求。
    • 这篇工作最重要的三点设计：
    • tool 与 skill 的区分：skill 不是单个函数或 prompt， 而是包含 instructions、scripts、references 的多文件 package， 因此生成难度和验证难度都远高于 tool generation。
    • co-evolutionary verification：由于真实环境通常只给 pass/fail， 看不到隐藏测试细节，所以作者让 verifier 独立构造 proxy tests， 把稀疏 reward 变成高密度、可执行的修正反馈。
    • iterative refinement + test escalation：当 proxy test 通过但 oracle 仍失败时， 不是只改 skill，也会继续强化 verifier 的测试集， 让“修 skill”和“补验证标准”同步演化。
    • 这篇论文最值得记住的判断是：skill 质量不只取决于 generator， 也取决于 verifier 能不能持续制造足够接近真值的训练压力。
    • 和人工 skills / one-shot self-generation 相比， CoEvoSkills 强调的不是“更会写”，而是“更会在外部反馈下持续修正”， 这也是它能超过 human-authored skills 的关键原因。
    • 对我工作的启发：如果做社媒翻译 agent 的 skill evolution， 重点可能不只是让 translator 生成更好的 skill， 还要让 evaluator / verifier 也随之演化；否则 solver 变强后， 静态评估器很容易失真、漏检，最终限制整个系统上限。

    7.31

    梳理memskill和skillrouter论文：

    • MemSkill 的核心 idea 是：agent memory 不该只靠固定的 add / update / delete 之类手工 operation， 而要把“怎么构造 memory”抽象成可学习、可进化的 memory skills。
    • 这篇工作最重要的三点设计：
    • memory bank / skill bank 分离：前者存某条具体 trace 的记忆， 后者存跨任务可复用的 memory behaviors， 因此系统学到的不只是“记了什么”，更是“该怎么记”。
    • controller + executor：controller 为当前 span 选 Top-K skills， executor 再在这些 skills 条件下一次性生成 memory updates， 用 span-level 处理替代逐 turn 记忆维护。
    • designer 驱动的 skill evolution：周期性分析 hard cases， 细化旧 skills、增加新 skills， 让 memory construction policy 和 skill bank 同时进化。
    • 这篇论文最值得记住的判断是：memory system 的关键不只是存储结构， 而是“记忆构造行为”本身能不能被持续学习和修正。
    • 和 MemoryBank / Mem0 / A-MEM 这类更偏静态 pipeline 的方法相比， MemSkill 真正改变的是：把 memory behavior 本身变成了 skill object， 因而能更自然地适应不同任务、不同历史结构与不同 agent 形态。
    • SkillRouter 的核心 idea 是：在大规模 skill registry 里， 决定 routing 成败的往往不是 skill 的 name + description， 而是藏在 skill body 里的功能细节； 只靠 metadata 会严重误路由。
    • 这篇工作最重要的三点设计：
    • body-access 诊断：在约 80K skill pool 上， 只移除 body 就让多种 retrieval / reranking baseline 的 Hit@1 下降 37–44 个百分点，说明缺失的是 body-resident signal， 而不是简单的文本长度优势。
    • body-aware retrieve-and-rerank：先用 encoder 从大池子里取 top-K， 再用 cross-encoder 基于全字段做细粒度重排， 把 body 真正纳入上游 skill routing。
    • false-negative filtering + listwise reranking：在 skill 高度重叠的池子里， 训练信号很容易被近重复 skill 污染， 而 pointwise loss 也不足以解决候选之间的细粒度竞争。
    • 这篇论文最值得记住的判断是：agent 不一定要一开始看到完整 skill body， 但 router 最好要能看到；否则上游 shortlist 一错，下游 agent 很难补救。
    • 两篇论文放在一起看，一个在研究 怎么把经验沉淀成更好的 skill / memory， 一个在研究 当 skill 数量爆炸后，怎么把对的 skill 找出来； 前者解决“skill 如何形成与进化”，后者解决“skill 如何在规模化生态里被命中”。
    • 对我工作的启发：如果以后做可演化的翻译 / 社媒 agent， 不只要考虑 skill 会不会生成和更新， 还要考虑 skill 数量变多以后，router 是否还能从大量相似技能中 稳定选中真正有用的那几个； 否则 skill ecosystem 越大，反而越容易在入口处失效。

    8.1

    梳理lightmem：

    • LightMem 的核心 idea 是：长时程 agent memory 的问题不只是“能不能记”， 而是现有系统通常把太多冗余原文、过细的更新粒度和过重的在线维护 一起塞进推理环路，导致 memory 成本过高。
    • 这篇工作最重要的三点设计：
    • sensory memory 预压缩：先用轻量压缩模型过滤掉大量低价值 token， 不让所有原始历史都直接进入 memory construction pipeline。
    • topic-aware short-term memory：不是按固定 turn / session 切块， 而是结合 attention 与 similarity 做 topic segmentation， 让后续摘要发生在更自然的语义单元上。
    • sleep-time long-term update：在线阶段先做 soft insert， 离线再并行整理、去重、更新， 把最昂贵也最容易出错的 memory consolidation 从实时推理里解耦出来。
    • 这篇论文最值得记住的判断是：memory system 不一定要每一步都立刻“整理好”， 很多时候先保住信息、后离线整合，反而更稳也更便宜。
    • 和 MemoryOS / Mem0 / A-MEM 这类偏重在线 memory maintenance 的方法相比， LightMem 真正改变的是：把 memory pipeline 明确拆成 “预过滤 → 短期组织 → 睡眠期更新”三层， 用更接近人类记忆的流程去平衡效果与成本。

    8.2

    梳理token pilot 论文：

    • TokenPilot 的核心 idea 是：context management 不能只看“压掉了多少 token”， 还要看这些压缩、截断和重排会不会破坏 backend 的 prompt cache 对齐； 否则上下文虽然变短，推理反而可能更贵。
    • 这篇工作最重要的三点设计：
    • ingestion-aware compaction：在消息进入上下文前先做 prefix stabilization， 把工作目录、时间戳、session id、tool schema 抖动等易变字段替换成稳定占位符， 同时对 HTML、日志、重复 read 结果做规则化减噪。
    • recoverable reduction：不是粗暴截断，而是把完整 payload 存进外部 registry， 默认只保留压缩视图，必要时再通过 recovery tool 取回全量内容， 以此兼顾轻量上下文和任务可完成性。
    • lifecycle-aware eviction：上下文片段不是任务一完成就删， 而是显式维护 active / completed / evictable 三态， 只有当 residual utility 真正耗尽时才移除，避免后续任务反复从头读同一份环境信息。
    • 这篇论文最值得记住的判断是：更短的上下文不一定更便宜； 如果它打断了 prefix continuity、诱发了更多 cache miss 和重复探索， 系统总成本反而可能上升。
    • 两篇论文放在一起看，LightMem 更像是在研究 agent memory 内部怎样分层、怎样更新才更省， TokenPilot 则是在研究 agent runtime 层面的上下文工程怎样设计，才能既压缩历史又保住缓存收益； 前者更偏 memory architecture，后者更偏 serving / inference systems。
    • 对我工作的启发：如果以后做长期运行的翻译 / 社媒 agent， 不能只想着“存什么 memory”或“删掉哪些历史”， 还要考虑这些操作是否会破坏缓存复用、迫使 agent 重新探索环境； 否则即使 memory 逻辑本身没问题，系统级成本也可能在长 session 中失控。

    8.4

    梳理d2skill 论文：

    • D2Skill 的核心 idea 是：技能库不能只做“轨迹级引导 + 静态复用”， 而要在训练中与策略协同进化——用任务技能（高层规划）+ 步骤技能（局部修正） 两层粒度组织经验，并通过配对 rollout 估计技能效用、动态检索与剪枝， 让“策略变强 → 技能更新 → 策略再变强”的闭环成立。
    • 这篇工作最重要的三点设计：
    • paired rollout 事后效用：同一策略下基线组与技能注入组各跑 N/2 条轨迹， 用两组成功率差构造事后信号——任务级信号共享给整组任务技能、轨迹级信用 \(c_i=Y_i-\bar Y_g^{\text{base}}\) 分给检索到的步骤技能，再以 EMA 更新每条技能的效用。
    • 两阶段检索 + 效用感知排序：先用相似度阈值召回候选，再用 “语义相似度 + UCB 式探索”打分注入 top-k；效用不只用于检索，还用于定期剪枝 （容量上限 + 保护窗口），防止技能库无界膨胀。
    • 反思生成双粒度技能：只在表现差时触发，从失败轨迹定位最早错误步骤 \(o_j\)， 产出任务技能（检索键 = 任务）与步骤技能（检索键 = (任务, 观测)），去重后入库。
    • 这篇论文最值得记住的判断是：技能不仅要“被积累”，还要在训练中被估值、被管理； 局部修正与全局规划同样重要。 消融中去掉技能管理下降最大（~10 个点）， 证实动态维护是关键增益来源；去掉任务/步骤技能任一也一致下降， 说明两层粒度缺一不可。
    • 与 SkillRL 的对比：两者都是“技能库 + 策略”联合，但 SkillRL 的技能是轨迹级引导、 每任务只检索一次；D2Skill 增加步骤技能（每步按观测检索）、显式估计效用并动态剪枝， 且技能生成与管理都在训练期、不依赖特权验证轨迹。
    • 分析里两个值得注意的点：① 评估时去掉技能库，D2Skill 训练出的策略仍不弱于 GRPO → 部分增益被内化进策略；② 训练开销接近 GRPO、约 1.7× 快于 SkillRL （批量嵌入检索 + 增量更新，低开销）。
    • 对我工作的启发：如果做社媒翻译 agent 的 skill evolution，技能层级除了“任务级策略”， 还应沉淀步骤级修正（例如某个局部文化检查点 / 翻译决策上的失败修复）；同时要像 D2Skill 一样给每条技能打效用分、定期淘汰，避免技能库越积越多反而污染检索。

    梳理xskill 论文：

    • XSKILL 的核心 idea 是：多模态智能体的持续学习不能只靠文本轨迹日志， 而要把“经验（action 级战术）+ 技能（task 级工作流）”两种互补知识 锚定在视觉观测上做提取与检索——无参数更新，纯靠外部知识库持续积累与改进。
    • 这篇工作最重要的三点设计：
    • 视觉锚定摘要 + 跨 rollout 批判：把交错图像观测与轨迹文本联合分析， 记录“什么视觉证据驱动了什么动作”，再对成功/失败轨迹做对比分析提炼因果因素， 产出经验更新（add/modify）与技能片段（工作流 + 工具模板，具体实体换占位符）。
    • 层级知识整合：经验按相似度阈值合并去重、超容量按泛化性删除； 技能文档逐节更新/合并/删除、超长时自评估精炼——把瞬时洞察沉淀为可泛化智慧。
    • 任务分解检索 + 上下文适配：把任务拆成多个抽象子任务分别检索经验， 再按当前视觉上下文改写经验、剪裁技能工作流与代码模板，以非规定性参考注入提示词。
    • 这篇论文最值得记住的判断是：多模态的决策信号在图像里，纯文本轨迹抓不住—— 知识提取与检索必须锚定视觉观测才能可靠检索、适配；同时消融显示 知识积累质量（Phase 1）比检索机制（Phase 2）更关键。
    • 两知识流互补的行为证据：技能把执行错误率 29.9% → 15.3%（语法/工具名错误大降， 专治“工具使用低效”）；经验改变工具选择分布（代码解释器占比上升，专治“编排僵化”）。
    • 分析里值得注意的点：① rollout 越多，跨 rollout 批判提炼的经验/技能质量越高； ② 跨基准零样本迁移优于全部基线；③ 跨模型迁移给弱/开源模型效果混合 （Average@4 下降但 Pass@4 因探索增加而上升）→ 基础模型能力是有效迁移的前提。
    • 与我之前读的对比：D2Skill 是“技能库 + 策略 RL 联合训练”（配对 rollout 打分）， XSKILL 是纯训练-free 的知识积累（不训策略），更接近 Ctx2Skill 的无参数路线， 但增加了“视觉锚定”这一多模态特有维度。
    • 对我工作的启发：做社媒翻译 agent 时，“锚定在什么信号上”值得借鉴——翻译的成败 信号虽在文本里，但文化差异、图片-文本对应的判断点也常依赖视觉/多模态上下文； 若要加入跨模型迁移，需注意弱模型可能被外部知识干扰。

    8.5

    梳理 veriskill 论文：

    • VeriSkill 的核心 idea 是：程序验证里的失败轨迹不是单纯的 bad case， 而是可以反向驱动 skill 进化的训练信号；它不是只修一次 prompt， 而是做一个 失败归因 → 诊断提炼 → 技能修正 → 再验证 的闭环。
    • 这篇工作最重要的三点设计：
    • 责任归因 (Attribution)：先判断一次验证失败是否真的来自技能缺陷， 避免把工具噪声、任务难度或偶然失败误判成 skill 问题；
    • 诊断性教训提炼 (Diagnostic Signatures)：把 verifier 的黑盒反馈压缩成 可复用的 lesson，而不是保留原始失败日志；
    • 可执行验证 (Executable Verification)：候选 skill 不能只“看起来更合理”， 还必须通过验证检查，且不能破坏程序语义。
    • 这篇论文最值得记住的判断是：程序验证场景里，skill 进化的关键不在于“会不会改”， 而在于能不能把稀疏、黑盒的失败反馈变成可执行、可筛选、语义安全的修正闭环。
    • 和一般的 skill self-evolution 方法相比，VeriSkill 更强调验证约束和语义保持； 和 CoEvoSkills / Trace2Skill 这些轨迹归纳类工作放在一起看，可以把它理解成 从“提炼经验”进一步走到“受约束地修复技能”。
    • 对我工作的启发：如果后续做翻译 / 评估 agent 的 skill evolution，不能只收集成功案例， 还要把失败归因和 verifier feedback 变成可复用的修正信号；否则 skill 只会越写越像经验总结， 很难真正形成稳定的自我进化闭环。

    一、主要工作

    在方法体系梳理方面，我以 Agent Skills 的基础概念为起点，系统阅读并梳理了 skill 方向十余篇核心论文，初步建立起对这一方法范式的整体认知：科研中的 skill 可视作把一段可复用、可迭代的指导性文本插入提示词上下文的 "harness"，其研究大致围绕自动生成与迭代（Ctx2Skill、Trace2Skill）、与自我进化机制结合（CoEvoSkills）、与策略训练的耦合（SkillRL、D2Ski ll）、多层级技能库组织（SkillX、MemSkill）、以及大规模 skill 的检索与上下文管理（SkillRouter、LightMem、TokenPilot）等方向展开。我还通读了 Ctx2Skill 的开源代码，理解了其"挑战者—推理者—评判者"自博弈循环、把成功与失败轨迹沉淀为自然语言技能、再经跨时间回放动态选择最优技能的完整流程，体 会到"真正随迭代演化的是技能文本而非模型参数"这一核心设计。

    在数据与评测方面，我深入了解了 CULTURE-MT 这一面向社媒 UGC 翻译的基准，认识到 BLEU、ChrF、COMET 等传统指标对文化差异几乎"失明"，而"文化有效性"——译文能否让目标语读者正确理解原意并产生相当的情感共鸣——才是社媒翻译真正的难点。我对相关 benchmark 做了系统核实与归类，发现既有基准普遍只覆盖"文化负载符号"这一维度、忽视 UGC 语言风格与情感共鸣，这恰是本课题可能的切入空白。

    在多智能体翻译方向的补充调研中，我梳理了角色分工、评估侧多智能体、对抗博弈、自精炼自奖励等主要范式，并结合 RIVAL、SCORE 等工作确认了课题的差异化位置：在社媒 UGC + 文化有效性场景下，用自然语言结构化评估器（而非标量奖励模型）与翻译器协同进化，并借鉴 Ctx2Skill 的跨时间回放机制抑制评估漂移——这一交叉点尚无先例。

    二、收获与认识

    这段实习让我在研究方法与科研素养上收获良多：一是理解了"从文献找空白、由空白定创新"的完整过程，认识到 novelty 是相对其他方法而言的，既要借鉴也须防止撞车；二是体会到 AI 辅助科研的实际价值——借助 AI 可显著加速文献梳理、代码理解与调研整理，但关键的方法判断仍需自己把关；三是对课题的认识从"概念模糊"走向"定位清晰"，明确了要解决什么问题 、采用什么范式、与哪些已有工作区分开，为下一步动手实践指明了方向。

    三、不足与下一步计划

    同时也应正视自身的不足：前期节奏不够稳定、整体进展偏慢；对核心方法的理解大多停留在框架层面，深度不足；尚未真正进入代码复现与实验阶段， 工程与复现能力有待加强。

    下一步我计划先复现代码开源的基线工作（如 Trace2Skill），读懂其具体实现后向社媒翻译与文化有效性方向迁移，搭建 translator / judge 两套 skill 协同进化的实验框架，跑通"初版方法到评测"的完整流程，再围绕性能与 novelty 反复迭代。
