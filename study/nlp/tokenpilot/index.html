    TokenPilot: Cache-Efficient Context Management for LLM Agents

    论文信息：Buqiang Xu, Zirui Xue, Dianmou Chen, Chenyang Fu, Chiyu Wu, Caiying Huang, Chen Jiang, Jizhan Fang, Xinle Deng, Yijun Chen, Yunzhi Yao, Xuehai Wang, Jin Shang, Gong Yu, Ningyu Zhang. arXiv:2606.17016v1, 2026.06。 论文原文 这篇工作关注的不是“怎么少放 token”本身，而是 怎样在压缩上下文的同时不破坏 prompt cache 命中， 用全局 compaction + 局部 eviction 兼顾效果与推理成本。

    图片占位符：论文 Figure 1，对比原始 agent loop 与传统截断/压缩系统， 说明后者虽然减少文本长度，却会因为前缀布局变化触发大量 cache miss。

    1. 摘要 (Abstract)

    • 核心问题：长时程 LLM agent 在持续多轮执行中会不断积累历史， 推理成本越来越高；但现有方法一旦频繁截断、压缩、重排上下文， 又会破坏 backend 的 prompt cache 对齐。
    • 核心矛盾：
    • 想要更少 token，就要做 pruning / compaction；
    • 但一旦输入布局不断变化，prefix continuity 被打断，cache hit 就会掉。
    • 核心想法：提出 TokenPilot，把 context management 分成两层：
    • 全局 Ingestion-Aware Compaction：在消息进入历史前先做稳定化与减噪；
    • 局部 Lifecycle-Aware Eviction：只有在上下文片段对当前任务真的失去残余价值时才移除。
    • 实验结论：在 PinchBench 与 Claw-Eval 上，TokenPilot 在不明显伤害任务效果的前提下，大幅降低推理成本，尤其在 continuous mode 下收益非常大。

    2. 引言 (Introduction)

    • 背景变化：LLM 正从聊天助手变成长期运行的 agent controller， 要调工具、文件系统、跨应用工作流，因此会持续产生长轨迹历史。
    • 直接后果：随着 session 越来越长，context window 被历史占满， 每一轮推理都变得更贵。
    • 现有路线：
    • 静态压缩：删 token、删句子、压 prompt；
    • 动态管理：summary、context folding、demand paging、外部 memory。
    • 作者指出的关键盲点： 很多方法只优化“文本长度”，却忽略了 serving 侧真正影响成本的一件事： prefix cache continuity。
    • 核心判断：
    • 光看文本少了多少，不够；
    • 还要看历史变动是否打断了 cache 对齐；
    • 有时“更短的上下文”反而更贵，因为它带来了更多 pre-fill miss。

    3. 相关工作 (Related Work)

    3.1 Static Content Compression and Abstraction

    • 一类工作关注在消息进入模型前就压缩文本，例如 token-level / sentence-level compression。
    • 还有一些方法把长历史改写成 summary、graph、episodic memory 等更抽象的表示。
    • TokenPilot 的差异：它不只问“压完还剩多少内容”，还问“压完以后还能不能保持 cache 对齐”。

    3.2 Dynamic and Runtime Scheduling

    • 另一类工作把 context window 当成运行时资源做调度， 例如 demand paging、context folding、virtual memory、memory OS。
    • TokenPilot 的差异：它把 runtime scheduling 与 prompt cache 连起来， 既管 eviction，也管 ingestion 时的布局稳定。

    4. 方法论 (Method)

    图片占位符：论文 Figure 2，展示 TokenPilot 的双层结构： 全局层负责 prefix stabilization 与 observation reduction，局部层负责 基于任务生命周期的 residual-utility eviction。

    4.1 优化目标：不是只压缩，而是提高“效用 / 成本比”

    作者把问题写成：

    • 给定原始历史 C，context management framework M 输出优化后的 C'；
    • 目标不是单纯最小化 |C'|；
    • 而是最大化 context utility / serving cost。

    这里的 serving cost 取决于两类 token：

    • cache hit tokens：复用已有 KV cache，成本低；
    • cache miss tokens：需要重新 pre-fill，成本高。

    所以 TokenPilot 的出发点很明确：

    • 不要只追求更短；
    • 要追求更高的有效信息密度 + 更稳定的缓存复用。

    4.2 全局层：Ingestion-Aware Compaction

    这一层发生在“消息进入上下文历史之前”，目的是先把最会破坏缓存的东西处理掉。

    4.2.1 消息分类

    作者把消息分成两类：

    • int internal intentional messages： 系统提示、思考、tool call、最终回答等，本身往往有较高 utility density；
    • env environmental feedback： 工具返回、网页内容、终端日志等开放世界反馈，通常充满结构噪声。

    TokenPilot 的立场不是“一刀切地压所有内容”，而是：

    • 对 int 重点保护 prefix 稳定性；
    • 对 env 重点做结构减噪与可恢复压缩。

    4.2.2 Prefix Stabilization

    • 很多 cache miss 不是因为任务变了，而是因为 prompt 前缀里混进了 工作目录、时间戳、session id、tool schema 抖动 这类运行时易变字段。
    • TokenPilot 会把这些动态字段替换成 稳定占位符，例如：
    • working directory → <WORKDIR>
    • timestamp → <TimeStamp>
    • agent id → <AGENT ID>
    • 同时把工具定义等容易随任务变化的内容移动到更靠后的动态区域，避免污染稳定前缀。

    这一步的核心不是语义压缩，而是 byte-identical prefix preservation。

    4.2.3 Observation Reduction

    对 env 类消息，TokenPilot 会做一组规则化 reduction pass，例如：

    • HTML slimming
    • 执行输出截断
    • 重复 read 去重
    • 格式清洗
    • 路径截断
    • 行号去除

    但作者没有直接做“不可逆删减”，而是引入：

    • artifact registry A[h(m)]：按内容哈希保存完整原文；
    • recovery tool：如果压缩后信息不够，agent 可以按需取回完整 payload。

    这意味着它采用的是：

    • 默认轻量展示；
    • 必要时再恢复全量内容。

    4.2.4 Access-frequency gate

    还有一个细节很重要：

    • 如果某类内容被反复访问，说明它并非低价值噪声；
    • TokenPilot 会根据内容哈希的访问频率提升该路径优先级， 停止继续激进截断。

    所以它不是死板规则，而是带有 usage-aware fallback 的入口压缩。

    4.3 局部层：Lifecycle-Aware Eviction

    如果说全局层解决的是“进入上下文前怎么放”，局部层解决的就是： 什么时候才能删。

    4.3.1 三态生命周期

    TokenPilot 为每段上下文片段维护三种状态：

    • active：当前任务仍在使用；
    • completed：该子任务局部完成，但上下文可能仍有残余价值；
    • evictable：残余价值已经消失，可以安全移除。

    最关键的一点是：

    • completed != 立刻删除。

    作者认为很多系统的问题就在于：

    • 一旦一个子任务做完，就马上 purge 它的上下文；
    • 但后续相邻任务经常还要用到这段历史；
    • 于是 agent 被迫从头 read / grep / scan 一遍。

    4.3.2 Residual Utility

    TokenPilot 显式建模一段上下文的 residual utility：

    • 只要对后续任务还有剩余帮助，就继续保留；
    • 只有当残余价值接近 0 时，才从 completed 进入 evictable。

    这让上下文管理从“看任务是否结束”升级为：

    • 看这段信息对后续任务是否还值钱。

    4.3.3 Batch-turn Estimation

    • 为避免每一步都触发状态估计造成抖动，作者不在每个 turn 都跑一次判断；
    • 而是每隔 B 个 turns 批量触发一次 estimator。
    • 默认最优设置是 B = 3。

    Estimator 会结合：

    • 显式完成证据；
    • 工具依赖模式；
    • 跨任务复用信号；
    • 压缩后的历史视图；

    来更新 registry 中各片段的生命周期状态。

    4.3.4 轻量状态估计器

    • 论文中用 Qwen3.5-35B-A3B 作为零样本 estimator；
    • 在 continuous PinchBench 上，估计器总成本不到 $0.03。

    也就是说，作者认为：

    • 如果能显著减少重复读取与 cache miss，
    • 那么引入一个小额的状态判断成本是完全划算的。

    5. 实验 (Experiments)

    5.1 实验设置

    • 评测基准：
    • PinchBench：123 个真实任务，11 个类别；
    • Claw-Eval (General)：161 个多步服务编排与分析类任务。
    • 两种模式：
    • isolated mode：每个任务开始前清空上下文；
    • continuous mode：同类别任务连续执行，历史持续保留。
    • 对比方法： Vanilla、LLMLingua-2、SelectiveContext、LCM、Pichay、Summary、 MemoBrain、AgentSwing、Keep-Last-N、MemOS。
    • 模型设置：
    • agent backbone 统一为 GPT-5.4-mini；
    • TokenPilot 的状态估计器为 Qwen3.5-35B-A3B。
    • 成本建模：按商业定价计算，区分 cache hit、cache miss 与 output token 成本。

    5.2 主要结果

    5.2.1 PinchBench

    • Isolated mode：
    • TokenPilot overall 81.0；
    • cost $3.22；
    • 明显低于 Vanilla 的 $8.31，也低于大多数压缩/分页基线。
    • Continuous mode：
    • TokenPilot overall 81.3；
    • cost $2.79；
    • 相比 Vanilla 的 $7.24，成本大幅下降，同时效果还更高。

    这里最值得注意的是：

    • TokenPilot 不是“牺牲效果换便宜”；
    • 在 PinchBench 上它反而同时拿到了更优或接近最优的效果与更低成本。

    5.2.2 Claw-Eval

    • Isolated mode：
    • TokenPilot overall 63.1；
    • cost $2.27；
    • 不一定是精度最高，但成本最低，属于很强的性价比点。
    • Continuous mode：
    • TokenPilot overall 60.8；
    • cost $10.58；
    • Vanilla 则飙到 $81.52。

    说明在真正长链、持续运行的 agent 环境里， 成本爆炸往往比 isolated benchmark 更严重，而 TokenPilot 的设计正好针对这个问题。

    5.3 消融实验

    Table 3 给出连续 PinchBench 上的渐进消融：

    • Vanilla：79.2 / $7.24
    • + Global Level：79.9 / $4.22
    • + Local Level：81.3 / $2.79

    这说明两层都有效：

    • 全局 compaction 主要负责减少 prefix miss；
    • 局部 eviction 进一步压缩活跃记忆占用；
    • 二者叠加后，既省钱又提升整体表现。

    5.4 Ingestion-Aware Compaction 分析

    Table 4 的 isolated 分析很有说服力：

    • Vanilla：80.47 / $8.31
    • + Cache Stabilization：80.81 / $4.35
    • + Reduction Pass：80.92 / $2.87
    • - Recovery Tool：77.12 / $4.03

    关键信息有三条：

    1. 稳定前缀本身就值很多钱
    2. 单加 placeholder stabilization，成本就几乎腰斩。
    3. 规则压缩在有 fallback 的前提下非常有效
    4. 进一步把成本压到 $2.87。
    5. Recovery tool 不能少
    6. 一旦禁用恢复机制，性能会明显掉，说明可恢复性是这套 compaction 真正可用的前提。

    5.5 Cache hit 与 reduction 行为分析

    图片占位符：论文 Figure 4，对比 PinchBench 与 Claw-Eval 在 Vanilla 和 Stable Placeholders 下的逐任务 cache hit rate。

    • 在 PinchBench 上，平均 cache hit rate 从 38.7% 提升到 79.2%；
    • 在 Claw-Eval 上，从 67.2% 提升到 83.1%。

    图片占位符：论文 Figure 5，展示 HTML slimming 与 execution truncation 为不同任务节省的字符数。

    • HTML slimming 最多可去掉 115k 字符的结构噪声；
    • 执行日志截断最多可去掉 883k 字符。

    这部分证明作者的主张：

    • 真正浪费上下文预算的，往往不是 reasoning text， 而是开放世界 observation 里的结构垃圾与超长日志。

    5.6 Lifecycle-Aware Eviction 分析

    图片占位符：论文 Figure 6，比较不同 batch size B 下的 cache miss、cache read、context window 与 cache hit rate。

    • 不做 eviction：历史无限增长，成本最高；
    • B = 1 太激进：虽然经常清理，但会破坏布局稳定，反而增加 miss；
    • 更大的 B：更有利于保持 cache continuity；
    • B = 3：是论文里在效果、成本、命中率之间最平衡的点。

    图片占位符：论文 Figure 7，在共享文件 transcript.md 的四任务轨迹中， 对比 TokenPilot 与无 residual utility estimation 版本的工具调用模式。

    这个例子非常直观：

    • 有 residual utility gate 时，后续任务可以直接定位相关片段；
    • 没有它时，每个新任务都要从文件开头重新 read、重新 scan、重新 grep。

    作者想说明的是：

    • context eviction 的问题不只是“删早了”；
    • 更严重的是它会诱发 重复探索成本，让 agent 不断重新建立同一份环境认知。

    6. 分析 (Analysis)

    6.1 这篇论文最重要的 insight

    我觉得这篇工作的关键不是又发明了一个 memory store， 而是明确指出了一个常被忽略的 serving-side事实：

    对 agent 来说，更短的上下文不一定更便宜；如果它破坏了 cache prefix，对应的系统成本反而会更高。

    也就是说，它把 context management 的关注点从：

    • “还剩多少 token”

    推进到了：

    • “这些 token 是以怎样的布局被送进模型的”
    • “会不会引起更多 cache miss”
    • “删掉之后会不会逼着 agent 重新读一遍”

    6.2 TokenPilot 真正优化的是“上下文工程”

    这篇论文不像很多 memory work 那样强调：

    • 记忆结构更复杂；
    • 检索器更强；
    • 或训练了更聪明的 summarizer。

    它更像是在做 context engineering / inference systems engineering：

    • 全局层面，让上下文从第一步开始就更适合缓存复用；
    • 局部层面，让历史删除遵循任务生命周期而不是盲目时间顺序。

    所以它的贡献边界很清楚：

    • 它主要优化 agent runtime efficiency；
    • 不是提升 reasoning 上限，而是减少不必要的推理开销。

    6.3 为什么 continuous mode 里的收益更大

    论文里最有说服力的结果其实在 continuous mode：

    • isolated mode 下，很多 baseline 还能靠“每题重置”避免上下文爆炸；
    • continuous mode 下，长时程历史的坏处会不断累计；
    • 此时 prefix stability、残余价值判断、恢复式压缩才真正体现出系统级优势。

    这说明 TokenPilot 更适合真实生产场景，而不只是单任务 benchmark。

    7. 结论 (Conclusion)

    • TokenPilot 提出了一个 双粒度 context management framework：
    • 全局上做 ingestion-aware compaction；
    • 局部上做 lifecycle-aware eviction。
    • 它最核心的贡献不是“压更多”，而是：
    • 在压缩的同时保住 cache hit；
    • 在删除历史前判断 residual utility。
    • 在 PinchBench 与 Claw-Eval 上，尤其是 continuous mode 中， 它大幅降低了长时程 agent 的推理成本。

    局限性 (Limitations)

    • estimator 在高歧义、弱信号交互里可能误判上下文状态；
    • 频率阈值与 batch size B 需要按部署环境调参；
    • prefix stabilization 依赖后端支持 prefix caching；
    • 论文中的 continuous mode 主要按同类任务连续分组， 对高度异质、强混排的真实流式任务序列仍需进一步验证。

    8. 一句话总结

    TokenPilot 的核心价值是把 context management 从“删多少历史”升级成“如何一边控制历史增长、一边维持 prompt cache 命中”，因此它更像一套面向长时程 agent 的上下文运行时系统。
