    问题定义（草稿）

    研究方向：社媒翻译与评估智能体协同进化 草稿日期：7.17 依据：Ctx2Skill（方法）、CULTURE-MT（任务与数据）、multi-agent-translation-survey（相关工作定位） 状态：初稿，待 RIVAL 全文读完后校准差异化表述

    一、要解决的问题（一句话）

    在社媒 UGC 跨文化翻译任务上，让翻译智能体与评估智能体以不更新参数的方式协同进化，并克服迭代过程中评估器漂移 / 被套利的问题，从而持续提升译文在"文化有效性"维度上的质量。

    二、难点（为什么这事儿难）

    难点 1：社媒 UGC 翻译的"文化有效性"难以定义、更难以自动度量

    • 社媒 UGC 的好译文不等于字面正确：梗、俚语、流行文化指涉、夸张/反问等 UGC 语言风格，以及文化负载符号，需要译文让目标语读者正确理解原意并产生相当的情感/社交共鸣（CULTURE-MT 的"文化有效性"准则）。
    • 传统指标（BLEU/ChrF/COMET）对文化差异几乎失明（CULTURE-MT 用 15 个模型已证）；文化有效性是新生维度，缺乏可大规模调用的可靠自动评估器。
    • CULTURE-MT 训了 JUDGER（微调 Qwen3-32B）来做这件事，但权重不开放，仅可经排行榜提交托管评测，无法在训练 loop 中高频调用。

    难点 2：无可靠外部反馈下的"协同"如何成立

    • 翻译器要进步，需要评估器反馈；评估器要进步，又依赖翻译器的产出作为"题面"。二者互相依赖、无外部裁判，形成 chicken-and-egg。
    • Ctx2Skill 已证明对抗式自博弈 + cross-time replay 可在"无外部反馈、不更新参数"下让 reasoning skill 协同进化；但它的协同发生在 Challenger↔Reasoner（出题/解题）两侧，没有"评估器"这个独立角色，也非翻译任务。

    难点 3：评估器在迭代中漂移、被套利

    • 静态评估器无法随翻译器进步而进步，优化压力会饱和（SCORE, arXiv:2606.04507 正式提出此痛点）。
    • 若评估器参与迭代，又会自发出现 reward hacking：评估器分涨而真实质量不涨（Spontaneous Reward Hacking, arXiv:2407.04549）。RIVAL 在字幕翻译上做 RM↔LLM 协同进化，仍受此困扰。
    • 评估器一旦学到表面捷径（长度、特定措辞），协同进化会沿着捷径坍缩，而非沿着文化有效性进步。

    三、已有工作及其局限

    工作 做了什么 局限（我的切入处）
    CULTURE-MT（任务/数据/评估） 提出文化有效性准则、建 1002×14×4 基准、训 JUDGER、证传统指标失明 JUDGER 是静态、权重式、不开放；仅做 self-refinement 单侧提升翻译器，未让评估器协同进化
    Ctx2Skill（方法框架） 冻结 LM + skill 文本协同进化；cross-time replay 防对抗漂移 协同在 Challenger↔Reasoner，无独立评估器角色；做通用 reasoning，非翻译；skill 单侧（解题侧）
    RIVAL（翻译域协同进化，最大撞车） RM↔LLM 交替更新、对抗 min-max、做字幕翻译 评估器是标量 RM（非 NL 文化有效性评估）；防漂移靠在线重训 RM + 定量奖励（重、且仍 reward hacking）；域是字幕非社媒 UGC；协同是对抗非协同式自博弈
    SCORE（协同进化范式，非翻译） evaluator↔solver 共享参数协同进化；点出"静态评估器饱和"痛点 做深度研究非翻译；防漂移靠 meta-harness + KL，非 cross-time replay
    SSR-Zero / TEaR（翻译自奖励/自精炼） reference-free 自评自改 评估器=策略自身（self-bias, arXiv:2402.11436），无独立可进化的评估器，单侧
    M-MAD（翻译评测多智能体） 多 agent 辩论 + MQM 维度做 MT 评测 仅评测侧、静态，不参与协同进化（可借鉴作评估器构造）

    综合空白：在社媒 UGC + 文化有效性翻译上，用 NL 结构化评估器（非标量 RM）与翻译器做双侧 skill 式协同进化（非对抗 min-max、非在线重训 RM），并以 Ctx2Skill 式 cross-time replay 抗评估器漂移（而非权重回滚/KL）——这一组合无人覆盖。

    四、创新点（三差异化，须与 RIVAL 精确区分）

    ⚠️ 不能宣称"首创 translator+evaluator 协同进化"——RIVAL 已做。差异化必须落到以下三点。

    1. 双侧 skill 式协同进化（对称）：翻译器与评估器均为"冻结强 LLM + 可迭代 skill 文本"。翻译 skill 进化让译文更贴合文化有效性；评估 skill 进化让评判更贴人工标注。进化的是文本而非权重——单次成本低、可存档可回滚，且两侧同构，使 cross-time replay 天然适用于评估器（Ctx2Skill 的 replay 原本只对解题侧 skill）。

    2. 任务域：社媒 UGC + 文化有效性：评估器是自然语言、维度化的文化有效性评判（文化负载符号 / UGC 语言风格 / 情感社交共鸣），而非 RIVAL 的标量 RM 或通用 BLEU/COMET。以 CULTURE-MT 为数据与校准锚点，JUDGER/人工标注作外部尺子，loop 内部用可调用的冻结 LLM + 评估 skill。

    3. cross-time replay 抗评估器漂移：把 Ctx2Skill 的"历史 hard/easy 探测集 × 乘积解决率 × 拉普拉斯平滑"机制，从翻译器迁移到评估器——用固定探测集回放评估 skill 的历史版本，选既不偏向最易、也不偏向最难、且不被表面捷径套利的版本。直接针对 SCORE 指出的"静态评估器饱和"与 Spontaneous Reward Hacking 指出的"迭代评估器被套利"两个痛点，提供一条非权重式、非对抗式的防漂移路径。

    五、研究问题（RQ）

    • RQ1：双侧 skill 式协同进化，能否在社媒 UGC 文化有效性上持续提升翻译器，且优于单侧 self-refinement（CULTURE-MT 基线）与静态 LLM-as-judge？
    • RQ2：评估 skill 能否在迭代中向人工/JUDGER 标注收敛（kappa 上升），即评估器确实在"进化"而非停滞？
    • RQ3：cross-time replay 能否抑制评估器漂移/被套利——在有 replay 与无 replay 下，评估器是否学到表面捷径（用反例探测集检验）？

    六、可行性闸门（前置，必须先过）

    JUDGER 权重不开放，loop 内评估器只能用"冻结强 LLM + 评估 skill"代理。闸门实验：

    在 CULTURE-MT 标注子集上，"冻结强 LLM（GPT-4o / Qwen3）+ 初始评估 skill"打分，与人工标注 / JUDGER 公开分数的一致率（kappa）是否够用作 loop 内信号； 若不够，验证迭代评估 skill 能否把一致率拉上去（评估 skill 可进化性的直接检验）。 通过 -> 进 loop；不通过 -> 考虑自训评估器（CULTURE-MT 1002 条 + M-MAD 辩论增强）作为 fallback。

    七、待办与风险

    • 必读：RIVAL 全文（校准差异化 §4，确认其 reward hacking 失败案例与评测设置）；SCORE §3.3-3.5（meta-harness 设计，对比 replay 防漂移）。
    • 风险 1：评估 skill 迭代后仍逼近不了 JUDGER 一致率 -> 闸门失败 -> fallback 自训评估器，成本上升。
    • 风险 2：双侧 skill 协同可能双方互相"合谋"走向捷径（评估器偏好某种译文风格，翻译器迎合）-> 这是 RQ3 要检验的，replay 是缓解手段；若 replay 不足，可能需引入人工锚点周期性校准。
    • 风险 3：与 RIVAL 差异化若表述不精，审稿人可能判 incremental -> §4 三点须有实验直接支撑（消融：标量 RM vs NL 评估器；对抗 vs replay；单侧 vs 双侧）。

    下一步：读 RIVAL 全文 → 据此校准 §4 → 跑可行性闸门 spike。
