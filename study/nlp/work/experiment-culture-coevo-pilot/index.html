    社媒翻译协同进化可行性验证实验（Pilot）

    目标：验证把 Ctx2Skill 式"双侧 skill 协同进化 + cross-time replay"迁移到社媒 UGC 文化有效性翻译上的可行性，形成可跑通的端到端 pipeline。 预期产出：① 一套轻量可复现的实验脚本；② translator skill / evaluator skill 的进化曲线；③ cross-time replay 是否抑制漂移的初步证据。

    1. 实验目标与假设

    1.1 核心问题

    在 CULTURE-MT 数据上，冻结 LLM 参数，仅迭代自然语言 skill，能否让： - 翻译器（Translator） 的译文在文化有效性维度上持续提升； - 评估器（Evaluator） 的打分与人类 / JUDGER 标注越来越一致； - cross-time replay 比"直接取最新 skill 版本"更稳定、更少 reward hacking。

    1.2 待验证假设

    • H1（可进化性）：evaluator skill 迭代后，与 JUDGER/human 的 kappa 高于初始 prompt。
    • H2（协同增益）：双侧协同（translator + evaluator 同时进化）优于单侧 self-refinement（仅 translator 进化）。
    • H3（replay 防漂移）：cross-time replay 选出的版本，在 hold-out probe set 上与 JUDGER 一致率优于"always latest"。

    2. 数据与资源

    2.1 数据集

    • CULTURE-MT：Wulinjuan/CULTURE-MT（HuggingFace）。
    • 规模：1,002 条中译英社媒 UGC，14 领域 × 4 类型。
    • 字段：source（中文原文）、translation（人工参考译文）、score（人工文化有效性分数 1–5）、domain、type。
    • Pilot 子集：为快速验证，先抽取 300 条。
    • train（进化池）：150 条
    • dev（replay 探测集 / 验证）：100 条
    • test（最终评测）：50 条
    • 分层抽样：按 domain + type + score 分层，保证各分数段都有样本。

    2.2 外部尺子（仅用于评估，不进入训练 loop）

    • 若 JUDGER 开放或可通过排行榜批量获取：用 JUDGER 分数作金标准。
    • 否则：用 CULTURE-MT 自带人工 score 作金标准，并额外用 GPT-4o/Qwen3-32B 做第三方 LLM-as-judge 参照。

    2.3 模型

    • Backbone（冻结）：Qwen3-32B-Instruct 或 GPT-4o-mini。
    • 建议 pilot 先用 Qwen3-32B（成本低、与 CULTURE-MT JUDGER 同族，便于对比）。
    • 所有角色（Translator / Evaluator / Skill Generator / Challenger）共用同一个冻结模型，仅通过 system prompt 和 skill 文本区分。

    3. 方法框架

    3.1 总体流程

    初始化：translator_skill_v0, evaluator_skill_v0
For iteration t = 1 ... T:
  1. 翻译：用 translator_skill_{t-1} 翻译 train/dev 样本 → 得到候选译文 C_t
  2. 评估：用 evaluator_skill_{t-1} 对 C_t 打分并写诊断 D_t
  3. 对比外部尺子：计算 evaluator 与 JUDGER/human 的一致率 κ_t
  4. 生成 translator skill patch：
     - 输入：source、参考译文、C_t、D_t、成功/失败标签
     - 输出： translator_skill patch ΔT_t → 生成候选 {translator_skill_t^1, ..., translator_skill_t^k}
  5. 生成 evaluator skill patch：
     - 输入：C_t、D_t、JUDGER/human 标签、误判案例
     - 输出：evaluator_skill patch ΔE_t → 生成候选 {evaluator_skill_t^1, ..., evaluator_skill_t^m}
  6. Cross-time replay：
     - 在历史版本 + 新候选中，用固定 dev probe set 回放，
     - 选使"乘积解决率"最大的 (translator_skill*, evaluator_skill*)
  7. 保存选中版本为 v_t
End
在 test set 上评估最终 v_T

    3.2 与 Ctx2Skill 的对应关系

    Ctx2Skill 角色 本实验角色 作用
    Challenger Challenger 从 train 中按难度/失败模式挑选下一轮要攻的样本（可选）
    Reasoner Translator 带 translator skill 做译文生成
    Judge Evaluator + 外部 JUDGER evaluator 给 loop 内信号；JUDGER 只作外部尺子
    Proposer/Generator Skill Generator 从成功/失败案例中提取 skill patch
    Cross-time replay Cross-time replay on both skills 同时回放 translator / evaluator skill 版本

    3.3 关键设计：双侧 skill 同构

    • translator skill 和 evaluator skill 都用同一套格式（YAML frontmatter + Markdown body）。
    • 这样 cross-time replay 的"乘积解决率"可以分别对两侧计算，也可以联合计算（见 §4.4）。

    4. Skill 格式与内容

    4.1 统一 Skill 模板

    ---
name: translator-skill-zh-en-ugc
version: v0
description: 面向中文社媒 UGC 中译英的文化有效性翻译技能
tags: [culture-mt, zh-en, ugc, translation]
---

# 角色
你是一位熟悉中西方社交媒体文化的译者，负责把中文 UGC 译成地道英文。

# 核心准则：文化有效性
译文应让英语读者**正确理解原意**并**产生相当的情感/社交共鸣**。

# 维度 1：文化负载符号
- 成语/典故/网络梗/品牌/地名等，优先找英语圈等价表达；
- 无等价时，用简短注释或意译保留情感色彩，不要硬翻字面。

# 维度 2：UGC 语言风格
- 保留原帖的语气（吐槽、种草、 sarcasm、夸张、emoji 感）；
- 避免过度书面化或广告语体。

# 维度 3：情感/社交共鸣
- 译文读起来应像目标语社媒用户会发的真实帖子；
- 若原文有互动感（反问、call out、tag），英文应保留同等互动感。

# 负面清单（会逐渐积累）
- 不要逐字对应导致英文生硬。
- 不要丢失原文的情绪峰值。
- 不要添加原文没有的信息。

    4.2 Evaluator Skill 模板

    ---
name: evaluator-skill-culture-mt
version: v0
description: 评估中译英 UGC 译文文化有效性的结构化 rubric
---

# 角色
你是文化有效性评估专家。对每一条(source, candidate translation)给出 1–5 分及诊断。

# 评分维度
1. 文化负载符号处理（1–5）：是否准确传递文化指涉。
2. UGC 风格保持（1–5）：语气、风格是否像真实英文社媒帖。
3. 情感/社交共鸣（1–5）：目标语读者能否产生相当情感反应。
4. 语义忠实（1–5）：是否遗漏或添加信息。
5. 语言流畅（1–5）：英文是否自然。

# 输出格式
```json
{
  "overall": 3,
  "dimensions": {"cultural_symbol": 3, "ugc_style": 3, "emotion": 3, "fidelity": 4, "fluency": 4},
  "diagnosis": "...",
  "suggestions": "..."
}

    常见误判警示（会逐渐积累）

    • 不要因英文"华丽"而给高分，要检查是否丢失原意。
    • 不要惩罚合理的文化替换（如用英语梗替换中文梗）。
    • 注意 sarcasm / 夸张是否被误读为字面意思。 
      ---

## 5. 每轮迭代详细流程

### 5.1 Step 1：翻译（Translator）

**System prompt**：
      You are a translator. Follow the skill below to translate Chinese social media UGC into English.

    SKILL

    {translator_skill} 

    **User prompt**：
    Source: {source} Domain: {domain} Type: {type}

    Please provide the translation only, followed by a one-line reflection on cultural choices. 

    输出：`candidate_translation`, `translator_reflection`。

### 5.2 Step 2：评估（Evaluator）

**System prompt**：
    You are a cultural-effectiveness evaluator. Follow the rubric below to score the candidate translation.

    RUBRIC

    {evaluator_skill} 

    **User prompt**：
    Source: {source} Candidate Translation: {candidate_translation} Reference Translation: {reference_translation}

    Output JSON only. 

    输出：`eval_json`（overall + dimensions + diagnosis + suggestions）。

### 5.3 Step 3：与外部尺子对齐（仅记录，不进入 loop）
- 用 JUDGER / human `score` 计算 evaluator 的：
  - Pearson / Spearman 相关
  - 四分类准确率（1–2 vs 3 vs 4 vs 5）
  - Quadratic Weighted Kappa
- 记录 translator 输出在 JUDGER 上的平均得分。

### 5.4 Step 4：生成 translator skill patch

**输入给 Skill Generator**：
- 当前 translator skill
- N 个成功案例（evaluator 与 JUDGER 一致且高分）：source → candidate → 为什么好
- N 个失败案例（evaluator 与 JUDGER 一致且低分，或 evaluator 误判）：source → candidate → 诊断

**Prompt**：
    You are improving a translation skill. Given the current skill and recent success/failure cases, propose 1–3 concrete patches. Each patch should be: - a new rule, - a refinement of an existing rule, - or a new entry in the "负面清单". Do not rewrite the whole skill; only output the diff-style patch in Markdown. 
    ### 5.5 Step 5：生成 evaluator skill patch

**输入给 Skill Generator**：
- 当前 evaluator skill
- 误判案例：evaluator 打分与 JUDGER/human 不一致的样本
- 成功对齐案例

**Prompt**：
    You are improving a cultural-effectiveness rubric. Given the current rubric and cases where your scores disagreed with human/JUDGER, propose 1–3 patches to: - clarify dimension definitions, - add new failure mode warnings, - or correct misweighted criteria. Output diff-style Markdown patch only. 
    ### 5.6 Step 6：Cross-time replay 选版本

这是本实验与 Ctx2Skill 最直接对应的部分。

#### 5.6.1 探测集（Probe Set）
- 固定为 dev 的 100 条（pilot 可 50 条），每轮不变。
- 按人工/JUDGER 分数分为：
  - **Easy set**：score ≥ 4（原文本身质量高或翻译难度低）
  - **Hard set**：score ≤ 3（文化负载重、风格强、容易翻车）

#### 5.6.2 版本回放
对每个 candidate translator skill 版本 T_i 和 evaluator skill 版本 E_j：
1. 用 T_i 翻译 probe set → 得候选译文 C_{ij}。
2. 用 E_j 对 C_{ij} 打分 → 得 predicted score。
3. 与 JUDGER/human 阈值比较：
   - 定义"解决"为 predicted score 与 gold score 同档（1–2/3/4/5 四档）。
   - 分别计算 easy set 解决率 `solve_easy(i,j)` 和 hard set 解决率 `solve_hard(i,j)`。

#### 5.6.3 拉普拉斯平滑与乘积准则
```python
solve_easy_smooth  = (n_easy_correct  + 1) / (n_easy  + 2)
solve_hard_smooth  = (n_hard_correct  + 1) / (n_hard  + 2)
score(i,j) = solve_easy_smooth * solve_hard_smooth
    - 选择使 score(i,j) 最大的 (i*, j*)。 - 与 Ctx2Skill 一致：乘积准则避免只选"解 easy"或只选"解 hard"的偏置版本。

    5.6.4 搜索策略（降低计算量）

    • 如果每侧每轮产生 k 个候选，T 轮后版本数为 O(Tk)。
    • 为控制成本，只保留最近 W 轮（如 W=3）的版本做 replay，或只保留每轮的"best so far"。

    6. 评估协议

    6.1 主指标

    角色 指标 说明
    Translator 平均 evaluator score 看 loop 内是否提升
    Translator JUDGER/human 平均得分 外部尺子验证
    Translator Pearson/Spearman vs JUDGER 译文质量排序是否对齐
    Evaluator Quadratic Weighted Kappa vs JUDGER/human 核心进化指标
    Evaluator 四档准确率 鲁棒性
    System Replay 选版 vs Always-Latest 的 κ 差 验证 replay 价值

    6.2 消融实验

    配置 含义 预期
    双侧 + Replay 完整方法 最优
    双侧 + No Replay（always latest） 验证 replay 作用 中后期 drift / kappa 下降
    仅 Translator 进化（static evaluator） 单侧基线 翻译器提升，但 evaluator 饱和
    仅 Evaluator 进化（static translator） 验证 evaluator 可进化性 kappa 上升，但译文不提升
    无 skill（zero-shot） 最弱基线 用于计算相对增益
    CULTURE-MT self-refinement 论文 reported 基线 对照

    6.3 漂移检测

    • 构造一个 shortcut probe set：
    • 例如，在译文中故意加入某些"高分表面特征"（更长的句子、更正式的词汇），但语义/文化质量其实下降。
    • 观察 evaluator skill 是否给这些样本虚高分数。
    • 如果 replay 版本的 shortcut probe 误判率显著低于 always-latest，说明 replay 抑制了漂移。

    7.1 主循环伪代码

    # run_pilot.py
from src.skill_manager import SkillManager
from src.replay import select_best_versions
from src.metrics import compute_kappa, compute_solve_rate

sm = SkillManager("skills/")
trans_skill = sm.load("translator_skill_v0")
eval_skill  = sm.load("evaluator_skill_v0")

train = load("data/train.jsonl")
dev   = load("data/dev.jsonl")
test  = load("data/test.jsonl")

history = [("v0", trans_skill, eval_skill)]

for t in range(1, T+1):
    # 1. translate
    preds = [translate(src, trans_skill) for src in train]
    # 2. evaluate
    evals = [evaluate(src, pred, ref, eval_skill) for src, pred, ref in zip(train, preds, refs)]
    # 3. generate patches
    trans_patches = propose_translator_patch(trans_skill, train, preds, evals)
    eval_patches  = propose_evaluator_patch(eval_skill, train, preds, evals, golds)
    # 4. candidate versions
    trans_candidates = [sm.apply_patch(trans_skill, p) for p in trans_patches]
    eval_candidates  = [sm.apply_patch(eval_skill,  p) for p in eval_patches]
    # 5. cross-time replay on dev probe
    best_trans, best_eval = select_best_versions(
        history + trans_candidates,
        history + eval_candidates,
        dev,
        golds_dev,
    )
    trans_skill, eval_skill = best_trans, best_eval
    history.append((f"v{t}", trans_skill, eval_skill))
    log_metrics(t, trans_skill, eval_skill, dev, test)

final_evaluate(history[-1], test)

    8. 超参与预算

    8.1 推荐超参（Pilot）

    参数 值 说明
    T（迭代轮数） 5–8 pilot 不必太深
    每轮 patch 数 k 3 控制分支
    Replay 窗口 W 3 只与最近 3 轮比较
    每轮用于生成 patch 的案例数 20（10 成功 + 10 失败） 按 error mode 聚类采样
    LLM temperature 0.6（翻译/评估） / 0.8（patch 生成）
    每次 API max_tokens 1024

    8.2 预算估算（300 条 pilot）

    • 翻译：300 × 5 轮 ≈ 1.5K calls
    • 评估：300 × 5 轮 ≈ 1.5K calls
    • Patch 生成：2 × 3 patches × 5 轮 ≈ 30 calls（可批量）
    • Replay：每轮最多 (3+1)×(3+1)=16 个组合 × 100 dev ≈ 1.6K calls × 5 = 8K calls
    • 总计约 12K LLM calls。若用 GPT-4o-mini，约 5–10 美元；若用本地 Qwen3-32B，主要为时间成本。

    9. 成功标准与失败判据

    9.1 视为"可行"的最小证据

    • evaluator skill 的 κ vs JUDGER/human 从 v0 的 < 0.3 提升到 v_T 的 ≥ 0.45。
    • 双侧进化的 translator 在 JUDGER 上平均得分高于 static translator（p < 0.05 或至少 0.3 点提升）。
    • replay 选出的版本在 dev probe 上的 κ 高于 always-latest 至少 0.05。

    9.2 视为"不可行 / 需调整"的信号

    • v0 evaluator κ 已 > 0.6：说明任务太简单，无需协同进化。
    • κ 不升反降：说明 patch 生成质量差，需改 prompt 或引入更多外部锚点。
    • 双侧协同明显低于单侧：说明 co-evolution 产生了合谋，需加正则（如固定探针、人工周期校准）。

    10. 风险与缓解

    风险 缓解
    JUDGER 不可本地调用 用人工 score 作金标准；同时用 GPT-4o 作第三方 judge 交叉验证
    Patch 生成导致 skill 膨胀 限制每轮 patch 数；定期由 LLM 压缩 skill；保留容量上限
    翻译器与评估器互相合谋 ① dev probe set 固定且不参与 patch 生成；② 定期用外部人工/JUDGER 校准；③ shortcut probe 检测
    成本过高 先用 150 条 micro-pilot；成功后再扩到 300 条
    模型调用不稳定 加 exponential backoff；结果缓存到 JSONL；支持断点续跑

    11. 与毕业设计/论文的衔接

    • 若 pilot 成功，可直接扩展为正式实验：
    • 数据集扩到完整 1,002 条 + CSM-MTBench 作跨域验证；
    • 引入多 evaluator skill（多维度 rubric，参考 M-MAD）；
    • 与 RIVAL、CULTURE-MT self-refinement 做完整对比；
    • 增加人工评估，验证文化有效性提升的可感知性。
    • 若失败，可快速转向 fallback：
    • 在 CULTURE-MT 上微调一个开源 judge（如 Qwen3-8B），再套协同进化框架。
