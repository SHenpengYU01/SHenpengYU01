    SkillRouter: Skill Routing for LLM Agents at Scale

    论文信息：YanZhao Zheng, ZhenTao Zhang, Chao Ma, YuanQiang Yu, JiHuai Zhu, Yong Wu, Tianze Xu, Baohua Dong, Hangcheng Zhu, Ruohui Huang, Gang Yu. Alibaba Group. arXiv:2603.22455v5, 2026.07。 论文原文 研究大规模 skill registry 下的 skill routing 问题，指出只看 name + description 会严重丢失关键信号，并提出紧凑的 body-aware retrieve-and-rerank 路由器 SkillRouter。

    图片占位符：论文 Figure 1，展示 skill body 对 routing 的关键性： 移除 body 后，不同 retrieval / reranking baseline 的 Hit@1 都显著下降。

    1. 摘要 (Abstract)

    • 核心问题：当 LLM agent 的 skill 生态扩展到上万、甚至数万条时， 不可能在推理时把所有 skills 一起暴露给模型，因此必须先做 skill routing：给定用户任务，先从 skill pool 中找出相关 skills。
    • 作者关注的现实设定：真实 agent stack 往往采用 progressive disclosure，也就是上游路由器可以看到完整 skill 文档， 但下游 agent 往往只先看到 skill 的 name 和 description。
    • 核心发现：在约 80K skills 的大规模候选池中，只隐藏 body， 就会让 routing accuracy 出现 37–44 个百分点 的下降。
    • 进一步结论：
    • 这不是简单的“文本更长所以效果更好”；
    • 即便把 body 压缩成更好的 description，仍然明显不如直接看全字段；
    • 即便只用 metadata 重新训练 encoder，也仍然落后 all-field 模型很多。
    • 方法：提出 SkillRouter，一个紧凑的、body-aware 的 retrieve-and-rerank pipeline。
    • 结果：1.2B 参数的 SkillRouter 在主 benchmark 上达到 74.0% Hit@1，比最强 base pipeline 更准，同时参数更小、延迟更低； 路由收益还能迁移到真实 coding agent 的端到端执行成功率上。

    2. 引言 (Introduction)

    • 背景：skills 已经成为扩展 LLM agents 的重要抽象， 把任务流程、工具用法和执行指导封装成可复用模块。
    • 现实约束：skill registry 规模很大时，不能把所有 skill 全塞进上下文， 必须先做路由。
    • 关键不对称性：
    • Router 可以看 skill 的全部字段；
    • Agent 最开始通常只能看到 skill 的元数据（名字、描述）。
    • 作者认为这个上游决策非常关键： 一旦路由器把错误 skill shortlist 暴露给 agent， 后面的 planning / execution 基本很难救回来。
    • 现有系统的默认假设：metadata 足够做 skill selection。
    • 这篇论文的问题意识：这个假设在 大规模、开放式、内容重叠很重的 skill registry 下未被系统验证。

    作者的目标不是泛泛讨论“tool retrieval 很重要”， 而是更具体地问：

    • skill 的哪一部分字段对 routing 最关键？
    • 在真实的 progressive-disclosure 设定里， 只靠 metadata 到底够不够？

    3. 问题定义与基准 (Problem Definition and Benchmark)

    3.1 任务定义

    给定：

    • 一个任务查询 q
    • 一个大规模 skill pool S = {s1, ..., sN}

    目标是检索出完成该任务所需的 ground-truth skill 集合 G_q。

    每个 skill 包含：

    • name
    • description
    • body（完整实现 / 指导内容）

    作者强调这里存在 hidden-body asymmetry：

    • routing system 可看全部字段；
    • downstream agent 最开始通常只能看到 metadata。

    3.2 评测指标

    • Hit@1：排第 1 的 skill 是否命中任一 ground-truth skill
    • MRR@10：前 10 内最靠前正确 skill 的倒数排名
    • Recall@K：top-K 中覆盖到的 GT skills 比例
    • FC@10：top-10 是否完整覆盖全部 ground-truth skills

    这里作者特别提醒：

    • 对 multi-skill 任务，Hit@1 只能说明“top-1 路由是否命中某个必要 skill”；
    • 但并不代表已经完整找齐全部 skills；
    • 所以还要看 Recall@K 与 FC@10。

    3.3 Benchmark 构建

    • 基于 SkillsBench 提供的 expert-curated task-skill mapping；
    • 从 87 个任务中去掉 12 个 generic-only case，保留 75 个核心查询：
    • 24 个 single-skill queries
    • 51 个 multi-skill queries
    • 候选池规模约 80K skills：
    • SkillsBench 技能
    • 大量开源 skill collection
    • 设计两个 tier：
    • Easy：78,361 skills
    • Hard：79,141 skills，在 Easy 基础上额外加入 780 个 LLM 生成的“看起来很像但功能不对”的 distractors

    Hard distractor 的三类策略：

    • 同领域但不同问题
    • 同技术但不同用途
    • 过度泛化的能力描述

    因此，这个 benchmark 专门测试的是：

    • 在超大候选池下的检索能力；
    • 在大量“看起来相关但功能不对”的候选之间的精细区分能力。

    4. 核心发现：真正决定 skill routing 的信号是什么？

    4.1 只看 metadata 会显著失效

    作者直接比较两种输入：

    • nd：只用 name + description
    • all-field：用 name + description + body

    结果非常强烈：

    • Qwen3-Emb-0.6B：Hit@1 从 56.0% 降到 18.7%
    • Qwen3-Emb-8B：从 64.0% 降到 25.3%
    • Qwen3-Emb-8B × Qwen3-Rank-8B：从 68.0% 降到 24.0%

    也就是说，移除 body 会带来 37–44pp 的性能崩塌。

    这说明：

    • 不是某个模型不行；
    • 而是 skill body 本身包含关键的 routing signal。

    4.2 不是“多一点文本就更好”这么简单

    作者做了几组更强的控制实验：

    (1) Oracle-ND：把 body 信息压缩成更好的 description

    • 用 GPT-5.4-mini 为 GT skill 生成 query-blind、body-informed 的短描述；
    • 再只用 name + 这个新描述 做 routing。

    结果：

    • 的确比原始 metadata 强很多；
    • 但仍然比 all-field routing 低 6.7–21.3pp。

    这说明：

    • body 中确实有可压缩成描述的信息；
    • 但压缩后的 metadata 仍然不足以完全替代直接访问 body。

    (2) Matched metadata-only fine-tuning

    • 只给 encoder 看 metadata，并且在训练和推理时都不暴露 body；
    • 和 all-field 版本使用同样的训练数据与负样本策略。

    结果：

    • nd-only fine-tuned encoder：51.3%
    • all-field fine-tuned encoder：65.3%

    仍有 14.0pp 的差距。

    说明：

    • 不是“metadata-only 模型训练不够”；
    • 而是 metadata 本身就不够表达 routing 所需的全部差异信息。

    (3) Length-controlled diagnostics

    作者还分析 attention：

    • body 虽然占绝大部分 token；
    • 但最终 attention 分布并不只是“因为 body 更长所以多看 body”；
    • body attention 和绝对 body 长度几乎不相关；
    • 在 description 更长的 quartile 中，all-field 的优势仍然很大。

    所以作者的结论很清晰：

    缺失的是 body-resident information，而不是长度带来的水分。

    4.3 这件事的意义

    当前很多 agent framework 隐含地把 metadata 当成检索入口； 但这篇论文说明：

    • 在大规模 skill registry、尤其是重叠严重的场景下， metadata 往往不足以做高质量 routing；
    • skill body 里才有真正区分“功能相近但不相同”的关键细节。

    这也直接引出 SkillRouter 的设计动机：

    • router 必须 body-aware。

    5. 方法：SkillRouter

    图片占位符：论文 Figure 2，SkillRouter 两阶段路由流程： 先用 bi-encoder 从约 80K skill pool 里取 top-20 候选，再用 cross-encoder 基于全字段重排。

    SkillRouter 不是发明全新架构，而是把标准 IR pipeline 做成适合这类场景的版本：

    • Stage 1：bi-encoder retrieve
    • Stage 2：cross-encoder rerank

    主配置是：

    • 0.6B encoder
    • 0.6B reranker
    • 总计 1.2B 参数

    5.1 Stage 1：Bi-encoder retrieval

    • 用 Qwen3-Emb-0.6B 做微调；
    • 训练数据是 37,979 个 synthetic (query, skill) 对；
    • query 由 GPT-4o-mini 根据 skill 的 metadata + body 生成， 但不能泄漏 skill 名称；
    • benchmark 中标注的技能不会出现在训练监督里，避免记忆 benchmark。

    训练目标：

    • in-batch InfoNCE
    • all-field skill input

    推理时：

    • 所有 skill 先离线 embedding；
    • 在线只做 query embedding + ANN 检索；
    • 先取出 top-20 候选给下一阶段。

    5.2 Hard negative mining

    作者认为 random negatives 不足以训练这种任务， 因为真实错误通常来自“看起来非常相关但其实不对”的 skills。

    每个 query 采 10 个 negatives，来源包括：

    • semantic negatives (4)：embedding 相近
    • lexical negatives (3)：BM25 相近
    • taxonomy negatives (2)：同一 skill category
    • random negatives (1)：跨类随机

    这样可以强迫 encoder 学会区分：

    • 语义近似项
    • 词面混淆项
    • 同类功能的细粒度差异

    5.3 False negative filtering

    大 skill pool 中，常常会出现：

    • 不同作者实现了几乎等价的 skill；
    • 名称不同，但功能接近或重合。

    如果把这种近似等价 skill 当负样本，会污染对比学习。

    作者用了三层过滤：

    1. 同名去重
    2. body trigram Jaccard > 0.6 过滤
    3. embedding similarity > 0.92 过滤

    总共移除了大约 10% 的 mined negatives。

    这一步在实验中贡献了 +4.0pp Hit@1。

    5.4 Stage 2：Cross-encoder reranking

    • 使用 fine-tuned Qwen3-Rank-0.6B；
    • 输入 top-20 candidates；
    • 对每个 query-skill pair 使用 flattened all-field 文本做打分。

    训练时，作者强调：

    • 在 top-20 这个阶段，候选通常全都“看起来像对的”；
    • 问题不是独立判断某个候选是否相关；
    • 而是要在多个强相关项之间做相对排序。

    所以作者采用：

    • Listwise cross-entropy，而不是 pointwise BCE。

    这点后来在实验里被证明非常关键。

    5.5 为什么 SkillRouter 本质上是“body-aware IR recipe”

    作者明确说了，他们的贡献不是新 encoder / reranker 架构， 而是针对这个特定设定给出的 recipe：

    1. 必须读 body
    2. 必须处理 false negatives
    3. 必须用 listwise reranking

    也就是说，SkillRouter 的核心不是模型结构创新， 而是把 IR pipeline 调到适合 skill routing 的 operating regime。

    6. 实验 (Experiments)

    6.1 Encoder-only 结果

    Table 3 的关键点：

    • Qwen3-Emb-0.6B：56.0% Hit@1
    • Qwen3-Emb-8B：64.0%
    • SR-Emb-0.6B：65.3%
    • SR-Emb-8B：68.0%

    说明：

    • task-specific fine-tuning 的价值， 比单纯把模型做大更重要；
    • 一个调过的 0.6B encoder， 甚至可以略胜 13× 更大的 base 8B encoder。

    6.2 Retrieve-and-rerank 主结果

    Table 4：

    • Qwen3-Emb-8B × Qwen3-Rank-8B：68.0% Hit@1
    • SR-Emb-0.6B × SR-Rank-0.6B：74.0% Hit@1
    • SR-Emb-8B × SR-Rank-8B：76.0%

    这意味着：

    • 1.2B 的 SkillRouter 主配置已经超过最强 16B base pipeline；
    • 而且是以更小的参数量、更低延迟达成的。

    6.3 对 multi-skill query 的解读

    作者很谨慎地指出：

    • SkillRouter 在 Hit@1 上最强；
    • 但在严格的 multi-skill 全覆盖指标 FC@10 上， 并不总是最好。

    例如 Table 5：

    • 在 multi-skill 上，SkillRouter 的 Hit@1 更高；
    • 但最强 base pipeline 在 FC@10 上略优。

    所以作者的主张是：

    • SkillRouter 最强的是 top-1 routing；
    • 不是说它在所有 exhaustive set recovery 指标上都全面领先。

    6.4 关键消融

    Table 6 的两点最重要：

    (1) False-negative filtering

    • clean negatives：65.3%
    • raw negatives：61.3%

    贡献约 +4.0pp。

    (2) Listwise vs Pointwise reranking

    • pointwise BCE：43.3%
    • listwise CE：74.0%

    差了 30.7pp。

    这说明：

    • 在重叠严重、候选都很像的 skill pool 中， pointwise 判别几乎不够用；
    • reranking 的核心是比较候选之间的相对关系。

    6.5 Supplementary benchmark

    作者还构建了 SkillBench-Supp：

    • 100 个 GT skills
    • 256 个单标签 query
    • 77K pool
    • 来自三个不同 skill source

    不重新调参，直接迁移 checkpoint：

    • Qwen3 16B pipeline：63.7% Hit@1
    • SkillRouter 1.2B：64.1%
    • SkillRouter 8B 版：73.0%

    说明 SkillRouter 的优势不是只在主 benchmark 上 overfit 得来的， 而是有一定跨源泛化能力。

    6.6 Downstream agent 端到端实验

    Table 8 / Appendix M：

    作者把路由结果喂给 4 个 coding agents：

    • Kimi-K2.5
    • glm-5
    • Claude Sonnet 4.6
    • Claude Opus 4.6

    结果：

    • top-1 设置下，SkillRouter 比最强 base router 平均提升 +1.78pp
    • top-10 设置下，平均提升 +2.33pp
    • 更强的 agent（如 Sonnet / Opus）收益更明显

    作者的解释也很合理：

    • 如果 agent 本身不会很好利用 skill，routing 再强也有天花板；
    • 越强的 agent，越能把正确路由带来的收益转化为成功率提升。

    6.7 Serving efficiency

    在真实 pool 的 GPU benchmark 上：

    • SkillRouter 1.2B pipeline：
    • p50 latency 495.8 ms
    • Qwen3 16B pipeline：
    • p50 latency 2900.1 ms

    也就是：

    • 5.8× 更快
    • GPU memory 还更低

    说明 SkillRouter 不只是“离线指标更高”， 也确实更适合作为线上 router。

    7. 分析 (Analysis)

    7.1 这篇论文最重要的 insight

    我觉得最关键的一句话是：

    Skill routing 的关键区别信息，经常藏在 body 里，而不是 metadata 里。

    为什么？

    • 很多 skills 的 name / description 写得很泛；
    • 真正区分“具体能做什么、边界在哪里、适用场景是什么”的信息， 往往在 body 里；
    • 在大规模重叠池里，这些细节恰好就是 routing 成败的决定因素。

    7.2 SkillRouter 的本质不是更大的模型，而是更对的 recipe

    这篇论文很值得注意的一点是：

    • 它不是靠堆更大的 router 解决问题；
    • 相反，它证明：
    • 更好的训练数据构造
    • 更干净的 hard negatives
    • 更符合目标的 reranking loss
    • body-aware 的输入方式

    往往比盲目增大参数更有效。

    这也是为什么 1.2B 的 SkillRouter 能打过 16B base pipeline。

    7.3 对 agent system 设计的启发

    这篇论文实际上在提醒 agent framework 设计者：

    • 如果 skill registry 很大， 不要默认 metadata 就足够做路由；
    • 如果上游 router 有权限看 body， 应该尽量利用 body 做索引或 rerank；
    • progressive disclosure 对下游 agent 有上下文成本优势， 但上游 router 不能因此自废武功。

    换句话说：

    • agent 不一定要读完整 body；
    • router 最好要能读完整 body。

    8. 相关工作 (Related Work)

    8.1 Large-scale tool / skill retrieval

    • ToolLLM、ToolRet、MetaTool 等工作关注大规模 tool selection / retrieval；
    • AgentSkillOS 关注 skill 的组织与 orchestration；
    • SkillsBench 关注 skill 使用能力本身。

    SkillRouter 的不同点：

    • 它不主要研究“拿到 skill 之后怎么用”；
    • 而是研究“在 80K 候选里，怎么把正确 skill 找出来”；
    • 并且把重点放在 field visibility：到底该索引哪些字段。

    8.2 Toolset construction and reranking

    • 论文使用的是标准的 bi-encoder / cross-encoder IR pipeline；
    • 和传统 dense retrieval / reranking 文献有明显继承关系。

    这篇工作的贡献不在 architecture novelty，而在 setting-specific diagnosis：

    • body access 是否必要；
    • false negatives 如何污染训练；
    • listwise rerank 为什么在 homogeneous skill pool 中必不可少。

    9. 结论 (Conclusion)

    • 在真实 registry scale 下，skill metadata 经常不足以支撑高质量 routing；
    • body-resident signal 是决定 skill selection 成败的关键因素；
    • SkillRouter 用一个紧凑的 body-aware retrieve-and-rerank recipe， 在准确率、效率与端到端 agent 成功率之间取得了很好的平衡。

    局限性 (Limitations)

    • 核心 benchmark 只有 75 个 expert-verified queries，规模仍偏小；
    • supplementary benchmark 虽然更大，但 query 是 LLM 生成的， 不是更广的人类标注验证；
    • downstream 实验只在 4 个 agents、统一 budget 下评估， 没有做更细的显著性分析；
    • 论文也承认：typed API repositories、垂直领域 catalog、 multi-hop retrieval 设定下，body-access 效应是否同样成立， 仍需进一步研究。

    10. 一句话总结

    SkillRouter 的核心贡献是证明了：在大规模 skill registry 中，真正决定路由质量的往往不是 skill 的名字和简介，而是藏在 skill body 里的功能细节。
